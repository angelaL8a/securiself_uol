# Sprint 4 — Manual Visual Evidence

The **eight PNGs in this folder** are the manual runtime evidence for Sprint 4:
`01`–`08`, captured by hand from the real running application with real Google
authentication. They are observations, not test output, and nothing here is
generated by an automated suite. Every file present in the folder is documented
below — there are no undocumented and no decorative images.

This file records the conditions the capture ran under, what each image shows,
and what may never appear in any of them; the same conditions apply to a
re-capture.

## Conditions the capture required

1. **Google Cloud credentials** (see `../sprint4-implementation.md` §7):
   - an OAuth 2.0 **Web application** client ID;
   - authorised JavaScript origin `http://localhost:3000`;
   - **no** authorised redirect URIs;
   - your own Google account added under **Test users** while the consent screen
     is in _Testing_.
2. **The same client ID in both files** — they must match exactly, because the
   browser requests the token with it and the backend verifies `aud` against it:
   - `GOOGLE_CLIENT_ID` in `apps/api-backend/.env`
   - `NEXT_PUBLIC_GOOGLE_CLIENT_ID` in `apps/securiself-platform/.env.local`
3. Apply the schema and start everything:
   ```bash
   pnpm --filter api-backend exec prisma db push   # adds User.googleId
   pnpm dev                                        # :8080 API, :3000 platform, :3001 PrymeCab
   ```
   **Restart the Next dev server after changing `NEXT_PUBLIC_GOOGLE_CLIENT_ID`** —
   `NEXT_PUBLIC_*` values are inlined at build time. If the Google button does
   not appear on `/sign-in`, this is almost always why.
4. **Journey A needs a pre-existing SecuriSelf account** whose email is the same
   as the Google account you will sign in with, and which already has at least
   one Context (otherwise the consent screen has nothing to offer). Create it
   with email/password _before_ touching Google — that ordering is the whole
   point of the linking evidence.
5. **Journey B needs a Google identity SecuriSelf has never seen.** Either use a
   second Google account, or delete the `User` row created in Journey A first.

### Capture rules

- Capture the **browser window including the address bar** for `02`, `04` and
  `06`. The URL _is_ the evidence in those three, and it contains no secrets —
  only `client_id`, `redirect_uri` and `returnTo`.
- For all other shots the address bar is optional.
- **Never** capture: DevTools with a network payload open, `localStorage`
  contents, any bearer token, an authorization code, the client secret, a
  password field with characters typed in it, or any `.env` file.
- The real Google account chooser (`03`) will show your real name, email address
  and avatar. Redact them if you do not want them published — the evidence value
  is that the Google-hosted UI appeared, not who you are.
- Use PNG. Keep the exact filenames below; the numbering is the reading order.
- If you add any file to this folder, document it here. Undocumented images are
  not evidence.

# Journey A — Google authentication inside the PrymeCab consent journey

This is the primary Sprint 4 path and the one that proves the most. `01`–`06`
were captured in a single unbroken browser session, signed out of SecuriSelf at
the start.

---

## 01-prymecab-login-entry.png

**Stage:** Start of the journey, before any authentication.

**Screen/state that must be visible:** The PrymeCab simulator landing page at
`http://localhost:3001`, unauthenticated, showing the **"Login with SecuriSelf"**
button and no profile card.

**Action to complete first:** Open `http://localhost:3001` in a browser with no
existing SecuriSelf session (use a private window, or clear the
`securiself.auth` key for `localhost:3000`). Do not click anything yet.

**What it demonstrates:** The journey genuinely begins at the third-party
application, not at a hand-typed SecuriSelf URL.

**What the reviewer should observe:** PrymeCab is showing its unauthenticated
state — it holds no profile and no session. This is the baseline the later
disclosure screenshots are measured against.

**Sprint 4 claim supported:** Provenance for `02`–`06`. Without this, a reviewer
cannot tell whether the `returnTo` in `02` was produced by the application or
typed by hand.

---

## 02-securiself-signin-google-option.png

**Stage:** SecuriSelf sign-in, reached by redirect from PrymeCab.

**Screen/state that must be visible:** The SecuriSelf `/sign-in` page showing
the email field, the password field, the "Sign in" button, the **"or"** divider,
and the **real Google-rendered "Sign in with Google" button**.
**The address bar must be visible** and must show
`localhost:3000/sign-in?returnTo=%2Foauth%2Fauthorize%3Fclient_id%3D…`.

**Action to complete first:** Click **"Login with SecuriSelf"** on `01`. PrymeCab
redirects to `/oauth/authorize?...`; because you are unauthenticated, SecuriSelf
bounces you to `/sign-in` with the full authorize URL preserved in `returnTo`.
Wait for the Google button to finish rendering before capturing.

**What it demonstrates:** Two things at once — that Google Identity Services
loaded and rendered Google's own button in the real application, and that the
consent request was parked in `returnTo` rather than discarded.

**What the reviewer should observe:**

1. The button is **Google's own rendered button** (Google's "G" mark and
   typography), not a SecuriSelf-styled imitation. This is the state no
   automated test could produce.
2. The email and password fields are still present and unchanged — Google was
   added as an alternative front door, not a replacement.
3. The address bar carries `returnTo=` containing the encoded `/oauth/authorize`
   URL with PrymeCab's `client_id`.

**Sprint 4 claim supported:** `GoogleSignInButton` renders the official GIS
button when `NEXT_PUBLIC_GOOGLE_CLIENT_ID` is configured; email/password
authentication is untouched; `returnTo` is captured before authentication.

---

## 03-google-account-chooser.png

**Stage:** Real Google authentication — the provider's own UI.

**Screen/state that must be visible:** The **Google-hosted account chooser
popup** (`accounts.google.com`), listing the Google account(s) available and
naming the application as configured on your OAuth consent screen.

**Action to complete first:** Click the Google button in `02`. Capture the popup
**before** selecting an account.

**What it demonstrates:** Real Google infrastructure was reached. This is the
single most important screenshot in the folder — it is the only evidence that
the flow is genuinely Google's and not a local stand-in.

**What the reviewer should observe:** The popup is served from
`accounts.google.com`, and it is a **popup**, not a full-page redirect — which
is what `ux_mode: "popup"` means, and why the implementation needs an authorised
JavaScript origin but **no** authorised redirect URI.

**Sprint 4 claim supported:** Google Identity Services is integrated using
Google's own mechanism in `ux_mode: "popup"`; the credential is obtained from
the real provider rather than fabricated.

_Redact your personal Google name, email and avatar if you do not want them
published. Do not redact the `accounts.google.com` origin — that is the point of
the image._

---

## 04-returnto-consent-restored.png

**Stage:** Return to SecuriSelf immediately after real Google authentication.

**Screen/state that must be visible:** The SecuriSelf consent screen —
**"PrymeCab wants to access an identity context"** — with the redirect target
`http://localhost:3001/api/auth/callback`, the list of your **pre-existing**
Contexts, the "Only the selected context is shared" notice, and the
**Deny** / **Approve & continue** buttons.
**The address bar must be visible** and must show `localhost:3000/oauth/authorize?...`.

**Action to complete first:** Select your Google account in the popup from `03`
and let it complete. Do **not** navigate anywhere yourself — the application
must choose the destination. Capture as soon as the consent screen settles.

**What it demonstrates:** The two central Sprint 4 guarantees, visible in one
frame:

1. **`returnTo` survived real Google authentication.** The browser is on the
   original authorize request, **not** on `/console`.
2. **The pre-existing account was linked, not duplicated.** The Contexts listed
   here belong to the email/password account created in the prerequisites.

**What the reviewer should observe:** The URL is `/oauth/authorize`, and the
Contexts shown are the ones that existed _before_ Google was ever used. A
duplicate account would present an empty list here — that is the failure this
screenshot rules out.

**Sprint 4 claim supported:** `resolveReturnTo` is shared by the Google and
password paths; `loginWithGoogle` links `googleId` onto the existing `User` row
by verified email instead of creating a second account; Context ownership is
preserved.

---

## 05-context-selection-payload-preview.png

**Stage:** Choosing what PrymeCab is allowed to see, inside the
Google-authenticated session.

**Screen/state that must be visible:** The consent screen with one context
selected (a **SOCIAL** context is the clearest), and the **"What PrymeCab will
receive"** payload preview expanded and legible.

**Action to complete first:** On the consent screen from `04`, click one context
and wait for the payload preview to render. Do not approve yet.

**What it demonstrates:** The contextual disclosure model applies unchanged to a
Google-authenticated session.

**What the reviewer should observe:** The preview contains **only** that
category's allow-listed fields (for SOCIAL: `display_name`, `username`,
`pronouns`, `avatar_url`). It contains **no root email**, no `legal_first_name`,
no `legal_last_name`, no `document_id` — and no Google-derived field of any
kind, such as a Google display name or Google profile picture.

**Sprint 4 claim supported:** No file in the disclosure path was modified; the
category allow-lists behave identically regardless of how the session was
obtained; Google profile claims were never persisted.

---

## 06-prymecab-context-disclosure.png

**Stage:** End of the journey — back in PrymeCab, authorised.

**Screen/state that must be visible:** PrymeCab at `http://localhost:3001`
rendering the profile it received: the context's display name, its category
badge, and the allow-listed fields. The **"Login with SecuriSelf"** button must
be gone. **The address bar should be visible** to show the browser is on
`localhost:3001`.

**Action to complete first:** Click **"Approve & continue"** on `05` and let the
redirect and PrymeCab's server-side token exchange finish.

**What it demonstrates:** The complete Sprint 4 path executes end to end with
**real** Google authentication:
PrymeCab → SecuriSelf → Google → SecuriSelf → consent → PrymeCab.

**What the reviewer should observe:** PrymeCab displays the _context_, never the
person — no root email, no legal name, no document ID, nothing from Google.
Compare directly against `01`: same application, now holding exactly one
context-bound profile and nothing more.

**Sprint 4 claim supported:** A Google-issued session drives the existing
OAuth-like consent, grant and filtered-disclosure chain without modification;
the third party receives the same filtered payload as under password
authentication.

# Journey B — A Google identity SecuriSelf has never seen

Proves the opposite case to `04`: when no account matches, one is created — and
Google's profile data does **not** flow into it. `07`–`08` were captured in a
second session, using a Google identity SecuriSelf had never seen.

---

## 07-new-google-user-console.png

**Stage:** First-ever sign-in for an unknown Google identity, with no `returnTo`.

**Screen/state that must be visible:** The authenticated SecuriSelf Console
overview at `localhost:3000/console`, with the account's email in the top bar
and the summary tiles reading **Identity completion 0%**, **Contexts 0**,
**Clients 0**.

**Action to complete first:** Sign out. Navigate **directly** to
`http://localhost:3000/sign-in` (no `returnTo`). Sign in with the Google account
SecuriSelf has never seen.

**What it demonstrates:** A new SecuriSelf account was created from a Google
identity and a working session was established — and it starts with nothing.

**What the reviewer should observe:** The **zeroes**. Google returns a name and
a profile picture, and none of it is here. Also note the destination: with no
`returnTo` present, authentication lands on `/console` — the fallback, and the
counterpart to `04`.

**Sprint 4 claim supported:** New-account creation from a Google identity;
`resolveReturnTo` falls back to `/console`; a Google-backed account begins with
zero Contexts and therefore discloses nothing until its owner chooses to.

---

## 08-new-google-user-empty-vault.png

**Stage:** The Vault of the freshly created Google-backed account.

**Screen/state that must be visible:** `localhost:3000/console/vault` with the
**legal first name and legal last name fields empty**, along with the other
unset Vault fields.

**Action to complete first:** From `07`, open **Vault** in the Console sidebar.
Change nothing.

**What it demonstrates:** The most privacy-critical Sprint 4 decision, made
visible. `loginWithGoogle` writes **only** `email` and `googleId`; it reads
`sub` and `email` from the ID token and discards `name`, `given_name`,
`family_name` and `picture`.

**What the reviewer should observe:** The legal name fields are empty even
though the Google account certainly has a name attached. `legalFirstName` and
`legalLastName` are the **only** root `User` fields any context category
(LEGAL) can disclose to a third party. Had Google's name auto-filled them,
Google profile data would silently have become third-party-disclosable data
without the owner ever deciding so. These empty fields are the evidence that it
did not.

**Sprint 4 claim supported:** No Google profile claim is persisted; the LEGAL
disclosure surface stays owner-controlled through the Vault.

# States deliberately **not** listed

These are omitted on purpose, so their absence is not read as an oversight.

| State                                                                          | Why there is no screenshot                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GOOGLE_CLIENT_ID` unset → backend `503`                                       | Backend-only. The frontend simply renders no Google button, so the screen is just the pre-Sprint-4 sign-in page.                                                                                                                                                                                                        |
| Missing `credential` in the request body → `400`                               | Backend-only; not reachable through the UI.                                                                                                                                                                                                                                                                             |
| GIS script fails to load → inline `role="alert"`                               | Only reproducible by blocking `accounts.google.com` at the network layer, which is not a genuine user-facing flow.                                                                                                                                                                                                      |
| Account linking by verified email, `user.count()`, `googleId` never serialised | Database and API-level facts. They are _inferred_ visually in `04` (the pre-existing Contexts appear), but the assertions themselves are not visual and belong to the automated evidence.                                                                                                                               |
