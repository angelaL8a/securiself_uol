## 6. Evidence paragraph for the report

The SecuriSelf API backend ships an integration test suite of 21 cases across
four files, executed with Vitest and Supertest against a real PostgreSQL test
database (provisioned via `TEST_DATABASE_URL` and Prisma `db push`, with all
tables truncated between cases for isolation). On the audited commit the suite
executed successfully and every test passed (4 test files, 21/21 tests, 74.20 s).
The tests cover four behavioural categories aligned with the project's evaluation
criteria. Functional correctness is demonstrated through registration, login,
session retrieval, vault updates, multi-context creation, the full OAuth-like
authorization-code-to-token exchange, filtered profile reads, and a health probe.
Privacy and data minimisation are verified by asserting that the SOCIAL,
PROFESSIONAL and LEGAL profile payloads expose only their permitted attributes
and that forbidden fields (legal names, document identifier, email, gender, job
title, company) are absent — including an explicit zero-leakage check on the
SOCIAL payload and confirmation that the root email is never returned. Security
and authorisation are exercised by rejecting expired, replayed, wrong-secret and
wrong-redirect-URI token exchanges and by rejecting missing, tampered and revoked
access tokens, while also confirming that an access token bound to one context
cannot read another. Audit logging is validated by confirming that
`ACCESS_GRANTED`, `PROFILE_READ` and `ACCESS_REVOKED` events are persisted and
returned newest-first. The suite therefore provides confirmed runtime evidence
for the backend's core flows, context-based privacy filtering, token and
authorisation failure handling, and audit-record creation, subject to the
coverage limitations noted below.

## 7. Limitations

- **Coverage gaps (no tests present for):** logout / token refresh, client secret
  rotation (`POST /clients/:id/rotate-secret`), context update / delete
  (`PUT` / `DELETE /api/v1/contexts/:id`), the `PRIVATE` context filtering rule
  (documented in the README but untested), input-validation `400` paths on
  register/login, cross-user ownership rejection (`403`), and consent denial
  (`approved: false`).
- **Happy-path bias in functional tests:** functional cases assert success
  responses; error and edge branches are mostly covered only within the security
  suite.
- **Audit depth:** tests assert that audit actions exist and are ordered, but do
  not deeply assert audit metadata (IP, user agent, application/context linkage).
- **Environment dependency:** execution requires a reachable PostgreSQL instance
  and `TEST_DATABASE_URL`; without them `global-setup.ts` throws and no tests run.
- **Scope:** this is a backend-only audit. PrymeCab end-to-end / cross-application
  integration is out of scope and not represented here (the "PrymeCab" client is
  only a fixture name in `tests/helpers.ts`).
